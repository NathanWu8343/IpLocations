
# Specification Template

## Guidelines

### 指導原則

- **文件目的**：完整定義要系統**如何做 (How)** 以及**做到什麼品質 (How Well)**
- **聚焦方向**：系統邏輯、資料設計、邊界條件
- **面向技術團隊**：確保內容對開發團隊易於理解並可直接執行
- **嚴守技術中立**：禁止包含 API、框架或程式碼等細節
- **獨立可測**：每個需求都必須能獨立測試
  
## Process Flow

### 1. 載入指導文件
讀取並提取關鍵資訊：
- `.bmad-core/steering/product.md` → 產品目的、核心功能、目標使用者
- `.bmad-core/changes/{feature-name}/prd.md` → 產品需求文件、使用者情境、使用者故事

**注意事項**：
- 取得 `prd.md` 全部的使用者故事，缺一不可

### 2. 分析需求

**分析流程（內部思考）：**
a. 逐一分析 `prd.md` 中的使用者故事和 `product.md` 的核心功能，
   將其拆解為具體的、獨立且可測試的功能性需求 (FR) 與非功能性需求 (NFR)
b. 對於不清楚的方面：
  - 優先依據上下文、使用者情境及業界標準進行推斷
  - 僅在無法合理推斷，且符合以下情況時才標記 `[NEEDS CLARIFICATION: 具體問題]`：
    * 功能範圍與邊界（包含/排除哪些使用案例）
    * 使用者類型與權限（若有多種解釋可能）
    * 數量級或效能要求（「大量」是多少？「快速」是幾秒？）
    * 安全性或合規性需求（涉及法律/財務時）
c. 識別關鍵元素：
  -  從需求中提取核心的**Key Entities**
  -  預測並列出重要的**Edge Cases** 與錯誤處理情境
d. 引用資訊時請標記來源 `[來源：文件名稱#章節或標題]`

### 3. 填寫範本內容

請依照下方 Template 結構，逐步、完整填寫每個章節內容：
- 所有描述必須清楚、具體且可驗證
- 嚴禁加入任何實作細節或技術方案

**如內容含 `[NEEDS CLARIFICATION]` 標記時：**
- 請於文件指定佔位符新增「## 待補充資訊」章節
- 以條列方式列出所有需澄清問題，格式如下：
  - `[問題描述]（章節：[章節名稱]）`
- 每個問題需明確標註所屬章節，便於後續追蹤

請確保每個章節內容均符合上述要求，並維持結構一致性。

## Template

以下為最終需求文件的 Markdown 範本：

```markdown
# Feature Specification

[如有需澄清資訊，插入以下章節]
## 待補充資訊

- [問題 1]（章節：[章節名稱]）
- [問題 2]（章節：[章節名稱]）

## Goals
[PRD 成功後將實現的一行期望成果的項目清單 - 使用者和專案的期望]

## Background
[1-2 個簡短段落，總結背景，例如我們在 PRD 中學到的內容，避免與目標重複，這解決了什麼問題以及為什麼，目前的概況或需求是什麼]

## Functional Requirements

- **FR-001**: 系統必須 [特定能力，例如，「允許使用者建立帳戶」]
- **FR-002**: 系統必須 [特定能力，例如，「驗證電子郵件地址」]
- **FR-003**: 使用者必須能夠 [關鍵互動，例如，「重設密碼」]
- **FR-004**: 系統必須 [資料需求，例如，「保存使用者偏好設定」]
- **FR-005**: 系統必須 [行為，例如，「記錄所有安全事件」]

*不明確需求標註範例：*

- **FR-006**: 系統必須透過 [NEEDS CLARIFICATION： 未指定驗證方法 - 電子郵件/密碼, SSO, OAuth?] 來驗證使用者
- **FR-007**: 系統必須將使用者資料保留 [NEEDS CLARIFICATION： 未指定保留期限]

## Non-Functional Requirements
- **NFR-001**: 系統應在 [NEEDS CLARIFICATION： 未指定負載量] 的同時支援至少 [NEEDS CLARIFICATION： 未指定使用者數量] 名使用者
- **NFR-002**: 系統應在 [NEEDS CLARIFICATION： 未指定時間] 內回應 95% 的請求
- **NFR-003**: 系統應符合 [NEEDS CLARIFICATION： 未指定標準] 的安全性標準
- **NFR-004**: 系統應具備 [NEEDS CLARIFICATION： 未指定備援需求] 的高可用性

## Key Entities *(若功能涉及資料則包含)*

- **[實體 1]**: [代表什麼、主要屬性（不含實作）]
- **[實體 2]**: [代表什麼、與其他實體的關係]

## Edge Cases

- 當 [邊界條件] 時會發生什麼？
- 系統如何處理 [錯誤情境]？

#### Dependencies
- 外部服務相依性
- 內部團隊相依性
- 先決工作

## Definition of Done (DoD)

- [ ] 所有需求均已實作並通過驗收標準
- [ ] 相關文件已更新且完整
- [ ] 程式碼已通過測試 (單元測試、整合測試、回歸測試)
- [ ] 無重大缺陷或阻礙問題
- [ ] 已完成程式碼審查並獲得批准
- [ ] 部署流程已驗證且可順利執行
- [ ] 使用者手冊或操作指引已提供 (如適用)
- [ ] 非功能性需求已驗證達標

```
