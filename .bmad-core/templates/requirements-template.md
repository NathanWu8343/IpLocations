# Requirements Template

## 撰寫規範

### 指導原則

- **以使用者為核心**：所有描述應聚焦於使用者或業務需求，避免系統內部細節
- **技術中立**：嚴禁提及任何框架、程式語言、資料庫或工具
- **合理推論**：根據上下文、產業標準及常見模式，適度補足未明確說明之處
- **業務導向**：以業務利害關係人為主要對象撰寫內容，而非開發人員
- **測試思維**：每項需求若有模糊處，應標註 `[NEEDS CLARIFICATION]`，以便後續澄清
- **可驗證性**：所有需求皆須可於不知實作細節下進行測試與驗證

### EARS 格式規範
所有驗收標準必須採用以下五種 EARS 格式之一：

1. **普遍性**： `[系統] 應 [動作]`
2. **事件驅動**： `當 [事件] 發生時，則 [系統] 應 [回應]`
3. **狀態驅動**： `在 [狀態] 期間，[系統] 應 [行為]`
4. **非預期行為**： `如果 [異常] 發生，則 [系統] 應 [處理]`
5. **可選功能**： `在 [條件] 下，[系統] 應能夠 [行為]`

**撰寫原則**：
- 避免模糊詞彙（如「快速」「簡單」）
- 確保每條標準可測試
- 優先使用事件驅動與非預期行為模式
- 禁止寫入實作方式（API、框架、程式碼）

## 執行流程


### 1. 載入指導文件
讀取並提取關鍵資訊：
- `.bmad-core/steering/product.md` → 產品目標、使用者需求

### 2. 分析功能描述
- 基於傳入的 `<feature-name>` 與 `<description>` 
- 分析功能描述，提取核心需求與關鍵資訊
- 識別功能範圍、使用者角色、預期效益

### 3. 分析需求

**規劃分析策略（內部思考）：**
- 根據功能描述與 `product.md`，拆解並細化需求
- 撰寫使用者故事，明確涵蓋主要角色、情境與動機
- 制定可衡量的成功標準，確保與業務目標一致
- 明確列出不在本次範圍內的事項，防止需求蔓延
- 識別所有需進一步澄清的資訊，並加註標記

**需澄清資訊的標註規則：**
- 使用格式：`[NEEDS CLARIFICATION： 具體問題]`
- 常見需澄清領域：
  - 功能範圍與邊界（包含/排除哪些使用案例）
  - 使用者類型與權限（若有多種解釋可能）
  - 數量級或效能要求（「大量」是多少？「快速」是幾秒？）
  - 安全性或合規性需求（涉及法律/財務時）

**注意事項：**
- 所有描述須清楚且可驗證
- 嚴禁包含實作細節、技術方案或程式碼

### 4. 填寫範本內容

依據下方 Template 結構，逐步填寫每個章節：

**如文件中出現 `[NEEDS CLARIFICATION]` 標記：**
- 於文件最前方新增「## 待補充資訊」章節
- 以清單方式列出所有需澄清問題：
  - `[問題描述]（章節：[章節名稱]）`
- 每個問題需明確標示所屬章節

### 5. 品質驗證

生成完成前，逐一確認以下檢查點：

- [ ] 所有區段已完成
- [ ] 文件中無實作細節、技術方案或程式碼
- [ ] 每個使用者故事都有 3-5 個驗收標準
- [ ] 所有驗收標準符合 EARS 格式
- [ ] 所有引用 product.md 的內容已標註來源
- [ ] 成功標準可量化
- [ ] 所有描述清晰且可驗證
- [ ] 有 `[NEEDS CLARIFICATION]` 標記時，需有「## 待補充資訊」章節


## Template

以下為最終需求文件的 Markdown 範本：

```markdown
# Requirements Document

[如有需澄清資訊，插入以下章節]
## 待補充資訊

- [問題 1]（章節：[章節名稱]）
- [問題 2]（章節：[章節名稱]）

## Introduction

[提供功能的簡要概觀、其目的以及對使用者的價值]

## Background

[總結背景，例如我們如何避免與目標重複，這解決了什麼問題以及為什麼，目前的概況或需求是什麼，解釋此功能如何支持 product.md 中概述的目標]

## Requirements

### Requirement 1

**User Story：** 身為 [角色]，我想要 [功能]，以便 [效益]

**Acceptance Criteria**
[條列式驗收標準，採用 EARS 格式]

### Requirement 2

**User Story：** 身為 [角色]，我想要 [功能]，以便 [效益]

**Acceptance Criteria**
[條列式驗收標準，採用 EARS 格式]

## Success Criteria

### 可衡量的成果

- **SC-001**： [可衡量的指標，例如，「使用者可以在 2 分鐘內完成帳戶建立」]
- **SC-002**： [可衡量的指標，例如，「系統可在 1000 個並行使用者下正常運作」]
- **SC-003**： [使用者滿意度指標，例如，「90% 的使用者在第一次嘗試時成功完成主要任務」]
- **SC-004**： [業務指標，例如，「將與 [X] 相關的支援問題減少 50%」]


## Out of Scope

- 明確排除的功能或需求
- 不在本次開發範圍內的技術或平台
- 非目標使用者群的相關需求
- 未來版本才考慮的擴充或整合
- 其他不屬於本專案目標的事項
```
