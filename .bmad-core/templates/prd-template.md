
# Specification Template

## Guidelines

### 指導原則

- **文件目的**：清晰定義使用者**需要什麼 (What)** 以及**為什麼需要 (Why)**
- **聚焦方向**：使用者價值、商業成果、體驗
- **嚴守技術中立**：絕不描述**如何實作 (How)**，禁止包含 API、框架或程式碼等細節
- **面向業務溝通**：確保內容對非技術背景的利害關係人易於理解
- **合理推測**：使用情境、行業標準和常見模式來填補空白
- **獨立可測**：每個使用者故事都必須能獨立測試
- **一致性**：使用標準化格式與術語，確保跨團隊協作順暢

### EARS 格式規範
所有驗收標準必須採用以下五種 EARS 格式之一：

1. **普遍性**： `[系統] 應 [動作]`
2. **事件驅動**： `當 [事件] 發生時，則 [系統] 應 [回應]`
3. **狀態驅動**： `在 [狀態] 期間，[系統] 應 [行為]`
4. **非預期行為**： `如果 [異常] 發生，則 [系統] 應 [處理]`
5. **可選功能**： `在 [條件] 下，[系統] 應能夠 [行為]`

**撰寫原則**：
- 避免模糊詞彙（如「快速」「簡單」）
- 確保每條標準可測試
- 優先使用事件驅動與非預期行為模式
- 禁止寫入實作方式（API、框架、程式碼）

## Process Flow

### 1. 載入指導文件
讀取並提取關鍵資訊：
- `.bmad-core/steering/product.md` → 產品目的、核心功能、目標使用者

### 2. 情境分析與需求拆解

**推論與分析流程（內部思考）：**

a. 基於傳入的 `<feature-name>` 與 `<description>` 
  - 分析功能描述，提取核心需求與關鍵資訊
  - 識別功能範圍、使用者角色、預期效益  
b. 結合功能描述與 `product.md`，進一步拆解並細化使用者情境
c. 對於不清楚的方面：
  - 優先依據上下文、使用者情境及業界標準進行推斷
  - 僅在無法合理推斷，且符合以下情況時才標記 `[NEEDS CLARIFICATION: 具體問題]`：
    * 功能範圍與邊界（包含/排除哪些使用案例）
    * 使用者類型與權限（若有多種解釋可能）
    * 數量級或效能要求（「大量」是多少？「快速」是幾秒？）
    * 安全性或合規性需求（涉及法律/財務時）
c. 針對所有使用者情境以優先度進行排序（P1 > P2 > P3），確保高優先情境優先處理，並記錄排序依據
d. 引用資訊時請標記來源 `[來源：文件名稱#章節或標題]`

### 3. 填寫範本內容

請依照下方 Template 結構，逐步、完整填寫每個章節內容：
- 所有描述必須清楚、具體且可驗證
- 嚴禁加入任何實作細節或技術方案

**如內容含 `[NEEDS CLARIFICATION]` 標記時：**
- 請於文件指定佔位符新增「## 待補充資訊」章節
- 以條列方式列出所有需澄清問題，格式如下：
  - `[問題描述]（章節：[章節名稱]）`
- 每個問題需明確標註所屬章節，便於後續追蹤

請確保每個章節內容均符合上述要求，並維持結構一致性。
